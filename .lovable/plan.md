## 2. Service worker

Two workers, deliberately separated, both live:

1. `/firebase-messaging-sw.js` at scope `/firebase-cloud-messaging-push-scope` — activated within the first seconds. Registered from `src/main.tsx`. Handles background push only.
2. `/sw.js` at scope `/` — the Workbox app shell generated by `vite-plugin-pwa` (`generateSW`, `registerType: "prompt"`, `injectRegister: null`). Registered via `useRegisterSW` inside `src/components/pwa/PWAUpdateBanner.tsx`, which only mounts the registering child when `shouldSkipServiceWorker()` is false (`src/lib/isPreviewHost.ts`). Confirmed: no registration in the Lovable preview/iframe/dev, registration does happen on `*.lovable.app`.

What it caches (read from the deployed `sw.js`):

- Precache manifest: 125 entries — `index.html`, `offline.html`, `landing-page.html`, `placeholder.svg`, all `/icons/*`, `/images/*`, and every hashed `assets/*.js|css|png`.
- Runtime: navigations → `NetworkFirst` (cache `html`, 15s timeout); backend REST → `NetworkFirst` (cache `supabase-api`, 5s timeout, 50 entries, 5 min TTL).
- `navigateFallback: /index.html` with an allowlist that excludes `/rest`, `/functions`, `/~oauth`, `/storage`, `/realtime`, `/sw.js`, `/firebase-messaging-sw.js`, `/assets`, `/icons`, `/manifest.json`, `/offline.html`, `robots.txt`.

Errors: zero console messages and zero page errors during a full first load, and no SW registration errors. The one measured concern is install duration — the cache filled from 21 to 125 entries over roughly **24 seconds** on a fast connection, i.e. first-visit offline readiness is not immediate and would be considerably slower on mobile data. `firebase-messaging-sw.js` is itself included in the app-shell precache, which means the push worker script can be served from Workbox's cache rather than the network.

## 4. Known iOS-specific issues on record

- Stored project knowledge: iOS standalone PWAs block `window.open()`, so all external links (WhatsApp, PDFs, certificates) must use anchor tags or the `openExternalUrl` helper, and WhatsApp sending goes server-side via the 360 Messenger Edge Function rather than `wa.me` deep links. This is already implemented.
- Stored project knowledge: popover/calendar pickers were replaced by native date inputs on mobile forms because of iOS reliability problems.
- Earlier in this project a production `ReferenceError` in the customer importer persisted after the fix shipped; the working conclusion was a stale service-worker cache on the user's device — consistent with `registerType: "prompt"`, where a user who never taps the banner keeps the old shell.
- `index.css` still contains `height: 100vh` / `min-height: 100vh` rules (around lines 200-204) with no `dvh` fallback, the classic iOS Safari dynamic-toolbar overflow.
- Installed iOS/Android apps cache `start_url`, `id`, `scope`, and `display` at install time, so those manifest fields cannot be changed for already-installed users without a reinstall.

## 5. Session / token storage

`src/integrations/supabase/client.ts` (auto-generated, lines 11-16) configures auth with `storage: localStorage`, `persistSession: true`, `autoRefreshToken: true`. So the access token, refresh token and user object live in a single `localStorage` key (`sb-<project>-auth-token`). No cookies, no `sessionStorage`, no PKCE `flowType` override (defaults apply).

Verified live: a signed-out visit leaves `localStorage` completely empty, so nothing is written before login.

iOS reliability implications of that choice:

- `localStorage` is script-writable storage, so Safari's 7-day cap on it can evict the session for users who don't open the app for a week; the visible symptom is a surprise logout. Installed home-screen PWAs on iOS 17+ get more durable storage than the browsing context, but eviction under storage pressure is still possible.
- Tokens are readable by any script on the origin, so third-party scripts on the page (the reb2b tag in `index.html`, Sentry, Firebase) sit in the same trust boundary as the session. That is inherent to the Supabase browser client's default, not a misconfiguration.
- Because the session is per-origin `localStorage`, it is not shared between Safari and the installed PWA — users must log in separately in each, and per-tenant custom domains each hold their own session.
- `autoRefreshToken` needs a foreground tab; iOS aggressively freezes backgrounded PWAs, so a long-suspended app can resume with an expired access token and depends on the refresh-on-resume path.

## Summary verdict

Installable, HTTPS, correct manifest, valid icons, both service workers registering on the live domain only, offline working after install, no runtime errors. The real weak points are: slow first-visit precache (~24s / 125 entries) so early-offline fails, a prompt-based update model that lets users sit on a stale shell, a square icon doing duty as maskable, no iOS splash images, leftover `100vh` rules, and `localStorage` sessions with iOS eviction/logout exposure.
